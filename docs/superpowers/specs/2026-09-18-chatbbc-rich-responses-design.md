# ChatBBC rich responses, native interactions and images — design

**Date:** 2026-09-18
**Status:** reviewed and revised; user authorized implementation planning on 2026-09-18. Application implementation has not started under this planning request.
**Scope:** ChatGPT assistant response presentation, media recording and user-initiated interaction in the existing ChatBBC workspace. Linux is the validation target. This feature must remain compatible with the app's Omarchy appearance work.

## 1. User problem and outcome

The same answer currently looks different in ChatGPT and ChatBBC. A choice prompt that ChatGPT renders as image-backed selectable cards and a Continue button appears in ChatBBC as raw component syntax. An ordinary rich diagram becomes visible tags, broken layout and horizontal overflow. The user separately tested **ordinary ChatGPT image generation** and reports that those images do not appear in ChatBBC either. This reproduces the reported missing-media symptom outside rich cards and makes standalone image generation a primary repair target.

The result must be a usable representation of the *same answer*: rich layouts, embedded reference images, generated images and functional controls. Choosing a card in ChatBBC chooses it in the original ChatGPT response; Continue operates the original button. A closed original browser tab can be reopened by an explicit interaction while that conversation remains the eligible active frontend, after verifying that it still shows the intended conversation, response and control. ChatBBC keeps a useful durable rendering when that original page is absent.

This is one end-to-end feature, with separately verifiable delivery increments. Working image-only responses are a first-class acceptance case, not a side effect of successfully recording assistant text or Markdown.

## 2. Agreed decisions and alternatives

1. **Native component mirroring:** Capture the browser's actual rendered result and a bounded semantic representation; paint a safe equivalent in ChatBBC with existing appearance tokens. Preserve stable local history. This is the selected architecture.
2. **Forward native actions:** Controls in the local representation represent original ChatGPT controls. A click authorizes one exact browser operation, not local evaluation of a model-authored callback. Reopen the original conversation on demand when required; verify the current target before acting.
3. **Whole-answer scope:** Support general rich response layouts, embedded images, standalone generated images and galleries, not only the example choice widget.
4. **Browser embedding alternative declined:** An Electron webview or second embedded ChatGPT runtime adds authentication, account state, browser ownership and lifecycle problems. Do not introduce it for this feature.
5. **Text-equivalent answer alternative declined:** Sending “I choose B” as a new prompt is not an equivalent substitute for clicking a native choice or Continue. Never silently translate an original UI action into a new chat message.
6. **Arbitrary component execution declined:** ChatGPT's model-authored component source, JavaScript, DIL-like syntax and inline event handlers are data. Neither the Electron renderer nor its preload evaluates them.

The existing `AGENTS.md` ownership and browser-opening rules still apply. An explicit human click provides a narrow reason to reopen the exact original chat; old history, loading a timeline and restoring a preview do not provide opening authority.

## 4. One representation and one owner per fact

Each canonical assistant message retains its authoritative raw text, canonical logical `messageId`, optional distinct raw `providerMessageId`, chronology and existing final/work state. A new optional **rich response revision** is an additional presentation projection tied to that exact canonical logical shard and its *originating* frontend conversation, local session and binding epoch. Compact & Resume may later attach a different frontend to that same durable session; it must not rewrite a historical rich message's provenance to the new frontend. Rich publication cannot create a message, infer a turn, advance `contentSeq`/`finalContentSeq`, mark Goal work done or replace authored text.

The representation is a bounded versioned tree, rather than captured arbitrary executable HTML. It contains semantic layout nodes (paragraph/heading/list, grouping, grid/row/column, cards, image slots, static illustration, diagram/chart presentation, and supported native controls), safe visible text, limited presentation tokens, stable node identifiers and references to independently stored media. Static unknown visuals may be captured as a bounded image of their *verified message-owned* region, accompanied by preserved text/accessibility content. Interactive unknown elements are shown with an explicit “Open in ChatGPT” fallback until their native action can be proved.

The canonical logical assistant `messageId` supplies the storage key; an independently verified current raw provider message identity and exact native DOM/Fiber relation supply the live surface association. An optional historical `providerMessageId` on its own is only drift evidence and does not authorize a click. A matching title, similar text, “only image in the answer,” screen position or current active tab is insufficient. The recorder may publish a raw text answer immediately and later enrich that **same** logical shard with rich layout and media as its native DOM hydrates. Image/HTML decoration alone does not count as assistant progress. Every asynchronous capture carries the original session, conversation, logical message, raw native association, binding and document epochs; the store accepts a revision only if that provenance and its predecessor still match. A snapshot from an old document must not overwrite a newer accepted revision after A → B → A navigation, app session rebind or page refresh. Historical messages from superseded conversations remain displayable but have no action authority on a retired frontend.

Ownership mapping:

| Fact | Owner and lifetime |
| --- | --- |
| Canonical message, turn, ordering and text | Existing `session/store.ts` and recorder; durable across app restarts and compaction. |
| Rich subtree and its display revisions | Exact assistant canonical message shard in the existing session store; no competing rich-history ledger. |
| Media bytes, asset quotas, deletion tombstones and retention | Existing `session/store.ts`/asset owner and `sessions:image` IPC; no remote URLs stored as assets. |
| Native element association and live control state | Extension page adapter/isolated content, only for its current document and exact message; old DOM refs do not survive navigation. |
| Action intent, exclusive election, dispatch and outcome | A narrowly specified main-process bridge owner with existing durable browser operation/receipt patterns; the extension owns the elected tab/document and actual native input. The separate browser-control RPC's process-memory pending map cannot serve as this durable owner. |
| Selection state shown in a historical card | Last verified browser observation attached to the exact rich message revision, labelled historical until reconfirmed; never just a local optimistic click. |
| Theme and visual presentation | Renderer CSS using current semantic appearance tokens and the planned Omarchy-compatible theme. |

The main process accepts a versioned schema with strict node/depth/count/text/byte/image budgets and validates every field independently. Initial upper bounds per complete rich message: 128 KiB serialized, 1,024 nodes, depth 24, 128 controls, 64 embedded-media references, and 8 KiB per text node; the whole observation batch must also fit the existing bridge request envelope. Enforce bounds before allocations, on the wire, on disk and in the renderer; return an explicit unavailable representation if any complete tree exceeds them, without taking a prefix or admitting media bytes inside tree JSON. Live evidence may justify a smaller limit during implementation; any larger limit needs a documented end-to-end budget review. `renderer` receives only validated structures and opaque local asset handles. Recording Off means no new local rich transcript, action-state record or image preview is saved; show the existing recording-disabled state and let the user open the original provider answer, without inventing a separate transient history/cache. Recording retention and session deletion must retire their associated media under the same existing policies. No page-supplied arbitrary CSS, raw HTML events, remote image loads, JS expressions, URLs for application actions, or unrestricted IPC names are admitted. The renderer's existing CSP, context isolation and preload allowlist remain intact.

## 5. Rich capture and display

### 5.1 Acquisition

Capture the whole public answer surface of an exactly identified provider message, including rich component roots outside `.markdown`, after checking current route, document/navigation epoch, provider id and selected local session binding. Capture text, semantic structure, safe presentation hints and control descriptions; media capture is asynchronous and separate. A probe that cannot make an exact message-to-DOM association must preserve canonical text and present an unavailable-rich-view explanation rather than borrow another answer's cards or images.

Support progressive hydration: record an initial structural revision, then update the exact same message when ChatGPT renders more nodes, resolves images, changes a selection or finishes the answer. Never copy arbitrary React internals or execute the model-authored component source to reconstruct an interface. Capture visible result and native accessibility semantics; inspect actual SVG/canvas/diagram behavior on the live page before choosing semantic export versus bounded visual capture.

### 5.2 Presentation

Render the semantic tree inside the existing transcript bubble with the same chronology, stable outer DOM identity and viewport-preservation rules. Map safe layout primitives into ChatBBC's responsive row/column/grid/cards, text sizes, spacing and color tokens. Images retain reserved aspect-ratio slots while loading; a missing image does not move the rest of the answer unpredictably. Wide diagrams and tables have deliberate contained scrolling or scaled fitting. Plain prose must wrap and no answer may widen the entire chat pane. Respect keyboard accessibility, labels, visible focus, reduced motion, zoom, Light/Dark and Omarchy palette.

Keep complete canonical text in history as the guaranteed source and copy/accessibility fallback. When it contains component source but the native rich representation is unavailable, the default presentation shows a clear “Rich content unavailable — open original in ChatGPT” card, with the source accessible on explicit expansion; it does not dump raw component tags into the primary transcript. If captured visible accessible text is exactly owned and safe, include it as a readable summary. When the answer is genuinely an authored code example, render its source normally: syntax alone cannot classify it as a rich UI. If the live rich tree exceeds bounds, store an explicit unavailable state and preserve the text; never show half of a malformed container. Old history without a previously captured rich tree stays readable with this fallback; it cannot be reconstructed from source code, and viewing history alone must not open a provider tab.

## 6. All image families

### 6.1 Standalone generated images

Preserve the existing `native_image` event keyed by exact provider message UUID + provider asset id, including distinct multiple images and an image-only final. Identify every **observed public image output family** on the signed-in page from provider-typed evidence first, then match image nodes to that identity. Cover tool-produced and assistant-produced output, single images and galleries; preserve model part order and message chronology. If an exact public assistant-message surface proves an image is visible but its provider payload cannot supply a validated native-image tuple, attach an explicit bounded unsupported-media indication to that **exact message** and a redacted discovery-stage diagnostic; never invent a `native_image` asset id or misattribute a free-floating page image. If even message ownership is unknown, record diagnostic-only evidence and show no invented transcript row. Every observed unknown family becomes an implementation fixture rather than silent omission.

Metadata must appear promptly with a reserved footprint. Capture begins only from an eligible public output whose native status and node prove available pixels; incomplete images stay pending. An exact source is checked again after every asynchronous pixel operation. Investigate the current fixed WebP quality/size gate as part of the live failure: a valid loaded image that exceeds the encoded-preview byte cap may need a bounded lower-resolution/quality encode before being marked unavailable. Any adaptive encoding retains the existing pixel, decoded-memory and asset-byte ceilings and records the actual preview geometry. Repeated observations enrich the original event and never mint duplicates or mark turn completion. A final answer that consists only of media remains visible and its exact native terminal proof stays separate from image metadata.

### 6.2 Images embedded within rich responses

Assign an image slot to an exact node in an exact canonical assistant message. Images in choice cards, illustrative diagrams and ordinary prose use the same bounded capture, fully decoded asset admission, quota and user-initiated cleanup as native generated images. Give inline images stable local asset handles and alt text where actually supplied. They remain in their original reading/order position. Do not turn an inline reference picture into a second unrelated “ChatGPT generated image” timeline row. Media slots first persist identity and availability metadata, then reference an admitted asset only after its validated bytes and message revision have committed; failed/late capture cannot publish an orphaned or wrong-message image.

Where an image is a generated output *also* referenced by a rich structure, share its existing provider tuple/local asset instead of recording two copies. Where the page offers only a rendered reference image, use a separate message/node-scoped presentation identity and local asset; an external URL is not a durable identifier or a credential to save. Never persist signed image URLs, cookies or raw provider request payloads. Do not fetch arbitrary external image URLs under app authority. Recover pixels from the already-loaded native page where permitted and proven. If an otherwise exact loaded cross-origin image cannot be drawn to canvas, investigate a page-owned, user-permitted screenshot cropped to its uniquely identified visible bounds, with fresh document/viewport/obstruction checks and existing screen permission. That path needs live proof it works through the paired companion without borrowing the agent browser-control debugger or disrupting a protected executor tab. Never retain surrounding page pixels or claim a successful capture from a blocked or ambiguous crop. An unsupported capture path gives an explicit unavailable state.

### 6.3 Image viewing and recovery

Clicking an available local preview opens an accessible larger local viewer within retained preview resolution. “Open original in ChatGPT” targets the exact native conversation/image after fresh verification for original resolution or provider-owned controls; a downscaled preview is not described as original bytes. A missing or oversized preview shows a real reason (waiting for load, unsupported source, invalid/tainted pixels, size limit, quota or explicitly removed). An explicit **Retry capture** may use one re-observation of the exact existing image and, when needed, one user-authorized reopening. It never regenerates the image, blindly refetches an expired URL or repeats a provider action. Missing result/ambiguous dispatch stays unconfirmed; the user may inspect the original.

Local previews and rich media count against the same existing global quota and cleanup controls. The current cleanup code enumerates `native_image`, user-message and tool-call asset references; extending assistant messages with rich media **requires extending that exact reference inventory and its durable retirement transaction** to handle rich nodes and shared assets before any bytes are deleted. Every shared asset reference is retired together, and stale capture completion cannot resurrect a retired asset. Preserve removed-asset tombstones across restart: re-observation must not silently refill images the user deliberately deleted. A user-triggered explicit recapture after a deletion requires an explicit choice and respects quota. Keep historical text, layout and image metadata when pixels are unavailable.

## 7. Native interactive controls

### 7.1 Supported control semantics

The first supported control set is the provided example: selectable card/radio-like choice and its Continue action. Extend the same contract to observed buttons, links, checkboxes, radio groups, selects, text inputs and other recognized controls as live evidence permits. A local control's kind, label, available options, current value, disabled state and relationship to its parent form/group come from the exact native message surface. It must be keyboard accessible and visually consistent with ChatBBC.

Each actionable node carries a bounded, opaque reference to its *meaning and exact source*: local session principal, originating provider conversation and binding epoch, canonical logical message key, distinct current raw provider identity when verified, rich structure revision, semantic node id, intended operation and expected current value/state. The opaque handle is an index into main-process/server-owned validated action state, not client authority or a replayable DOM selector. A process restart invalidates every old live handle; an explicit new user click can resolve the *durable descriptor* into a newly checked action intent only after the main process verifies its exact historical owner and a fresh native logical-to-provider-to-DOM join. If that join is unavailable, the control remains inert with an explicit original-chat fallback. Retain display state across app restarts, but never persist a raw DOM reference as live click authority.

### 7.2 User action transaction

The bridge owns one unique action UUID and a durable, owner-bound record per user click. Its phases are **intent accepted → opening authority spent if a tab must be opened → exact document elected → may-have-dispatched → observed postcondition or outcome unknown → receipt retired**. Persist the intent and opening/election changes before handing out browser authority. Critically, persist `may-have-dispatched` with `writeDurableNow()` **before granting the extension permission to invoke the control**; after that point, a crash, timeout, missing ACK or restart can never turn the action back into an unattempted click. The companion retains the matching result/ACK custody until the main process durably acknowledges it. The receipt and retirement must share one authoritative transition, and a late result must match the exact action UUID, session, conversation, message, document and generation. Before dispatch, a proven unused claim may fail visibly without a click; after dispatch is possible, reconcile by observation only and otherwise report unknown. No timer or app restart retries a possibly executed action.

1. A real user clicks a mirrored control in ChatBBC. The fixed preload API submits that exact action intent with its current displayed revision. The renderer accepts only a trusted user interaction on an explicitly mirrored control; captured markup and programmatic component events cannot call it. Loading/uncertain state is visible; no selection or “Continue succeeded” is asserted immediately.
2. Main checks current session ownership, originating/current conversation relationship, binding epoch, blocked/superseded/compacting state, exact message/node membership, live user action policy and available browser permission. The renderer-provided session id or handle alone is not authority. No model-authored event can trigger this route.
3. The existing companion elects a matching browser tab, or uses **one** explicit user-authorized opening of the stored conversation. It persists opening/claim custody before awaiting Chrome; tab-query failure is unknown, and a vanished opening result does not create a second tab. Reuse matching tabs without foregrounding them.
4. Once the page hydrates, verify exact conversation, document/navigation epoch, provider message/answer and a unique currently actionable control with matching semantic role, label/group and expected state. Re-observe the original control's value and enabled/selected state, especially after a closed tab or app restart: the saved selected card is historical evidence and cannot establish that the newly mounted React interface still has the choice selected. If native selection has reset, mark the display out of sync and require selection again before Continue; do not submit a different/default choice or automatically replay a previous click. If the old UI has changed, obtain a fresh rich snapshot and return a changed-interface result. Do not redirect to a text send, click by coordinates guessed from history or operate a nearest matching button.
5. Persist the durable may-have-dispatched cut before giving the companion its one native-action grant, then dispatch one browser-mediated input through the current verified page. Recheck state immediately before the operation. Use the page's real control through its observed interaction mechanism, never evaluate model-authored callback code or synthesize a successful result from local state. Observe the native postcondition on the same message/control (selection/value change, submission outcome, or provider's own terminal confirmation) and update the canonical display revision. A click acknowledgement alone is not a postcondition.
6. Commit the exact result and receipt retirement under the same authoritative transition. After lost acknowledgement, return “outcome unconfirmed”; reconcile by observing the original control if possible. Never automatically issue Continue twice or repeat another irreversible action. Explicit subsequent user actions require fresh observation and authority.

Native selection may be provisional while pending; persistent “selected” state requires observation. Submission controls must check the full current form/group value against the user's last verified intent, so a choice that was reset by reload cannot accidentally submit a default. Multiple controls cannot share an action id merely because their labels match. Newer questions, compaction A → B, wrong account/conversation, replaced message, changed options, user navigation or a late prior action invalidate the old pending route. A → B → A is checked against the generation/epoch, not only the final selected conversation id. No worker or unrelated prime may inherit a local session's action custody.

### 7.3 Availability and lifecycle

A historical card retains appearance and last observed state while the tab is closed. A user click can reopen its original conversation once **only while that frontend remains the active, eligible binding** for its local session; historical messages from superseded or blocked conversations remain displayable and have a manual-open option but are not actionable. If ChatGPT no longer exposes the answer/control, show a precise unavailable/changed message and an option to open the original conversation manually. A model-generated button that creates a new turn must not be treated as a mere local state update: the normal native user/turn recorder must observe the resulting conversation. Existing outbox ownership and native Send receipts continue to govern authored messages; this feature introduces no second chat-message queue.

Do not reopen conversations proactively during history paging, app startup, attachment hydration or a background timer. Browser-tab protection and normal idle closure resume once the explicit interaction is settled. Do not modify or borrow the general-purpose agent browser tool's lease for app-owned UI mirroring.

## 8. Interfaces and affected owners

The implementation plan should make the smallest coordinated changes across these boundaries:

- `extension/fiber.js`, `extension/chatgpt-dom.js`, `extension/content.js`: exact public message ↔ rich subtree/media association, bounded capture and native control observation/operation. `background.js`: one elected, explicitly user-authorized browser action and reopening with current document proof.
- `src/main/bridge.ts`, `src/main/session/recorder.ts`, `src/shared/session.ts`, `src/main/session/store.ts`: validate rich observations, retain canonical rich revisions and media associations, and own narrow action custody/receipts. A new action or observation wire contract requires a coordinated bridge-protocol and companion-version update in their existing declarations; mixed old/new installs must refuse incompatible actions instead of partially executing them.
- `src/main/ipc.ts`, `src/preload/index.ts`: fixed `rich action`, explicit retry/open-original and image-view routes with current permissions, named argument validation and exact session ownership. No general DOM/JS/URL invocation escapes the main process.
- `src/renderer/chat.ts` and focused rendering/interaction/media modules plus transcript styles: safe semantic layout, stable components, local image retrieval, keyboard/focus, stale selection generation fences and meaningful error states.
- `AGENTS.md`, user-facing guidance and focused tests/fixtures: document the new behavior and preserve the existing browser, history, storage and Omarchy design contracts.

Specific endpoint names and detailed DOM selectors follow the mandatory live DOM/media probe. The schema starts with the explicit bounds in §4, which can only change through the budget review specified there; no new generic command executor is allowed.

## 10. Completion criteria and limits

The feature is complete only when the two provided example answers can be viewed and used in ChatBBC and current ChatGPT-generated single, multiple and image-only outputs appear with durable previews. Switching chats, closing the original tab and restarting ChatBBC preserve their recorded representations. One real click on a supported control yields one correctly owned native action and an observed result, or a precise unavailable/unconfirmed result without acting on anything else. Accessibility, size/quota constraints, privacy, existing session/turn semantics and Omarchy appearance remain intact.

“General” means supporting observed public response/media families rather than promising that undocumented future provider payloads can be decoded without an update. Unknown future structures show a safe readable or visual fallback and keep the original answer available; they never execute source code, fabricate image bytes or claim native interaction when the original target cannot be verified. The full original-resolution generated file is provider-owned unless separately and explicitly acquired with supported evidence; a durable downscaled preview must be labeled as such.

The implementation plan is `docs/superpowers/plans/2026-09-18-chatbbc-rich-responses.md`. Preparing that plan does not authorize application implementation, packaging, installation or publication.
