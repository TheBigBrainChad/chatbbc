# Upstream 2.1.20 Migration Design

## Purpose

Bring ChatBBC forward from its current upstream source baseline, Chat On Steroids 2.1.18 at
`dee4b5e94b8598d7630e6db62bada9ac6050f457`, to the current upstream 2.1.20 tip at
`4e51a04d8e89a559e16d17fc7df6f547e57d666d` while preserving ChatBBC's current product identity,
ownership model, Linux-only release policy, Omarchy integration, and downstream behavior.

This is a semantic migration, not a Git-history merge. Every upstream commit in the range is
accounted for, but behavior is ported through ChatBBC's current authoritative owners rather than
replaying upstream assumptions over the fork.

## Success Criteria

The migration is complete only when all of the following are true:

1. Every one of the 29 upstream commits between the old and new baselines has an explicit final
   disposition.
2. Every upstream behavior we retain is implemented through ChatBBC's current ownership and
   identity boundaries.
3. No upstream change creates a second owner for a durable fact or weakens a fail-closed identity
   check.
4. Every upstream-changed path is either identical to the new baseline, mapped as an intentional
   downstream divergence, or recorded as an intentional translation/non-import.
5. ChatBBC retains its public identity: package/app/bridge/connector branding and protocol remain
   ChatBBC-owned.
6. ChatBBC remains a Linux x64 AppImage product with local verification and release tooling; hosted
   GitHub Actions and upstream macOS/Windows/ARM release behavior are not restored.
7. Browser-facing changes pass source tests and real signed-in ChatGPT acceptance where native page
   behavior is involved.
8. Only after the whole delta is accounted for does `docs/upstream-map.json` advance its upstream
   baseline to `4e51a04d8e89a559e16d17fc7df6f547e57d666d` / `2.1.20`.

## Immutable Migration Anchors

Old upstream baseline:

```text
dee4b5e94b8598d7630e6db62bada9ac6050f457
Chat On Steroids 2.1.18
```

New upstream baseline:

```text
4e51a04d8e89a559e16d17fc7df6f547e57d666d
Chat On Steroids 2.1.20
```

ChatBBC's own version is independent of the upstream baseline version. Importing upstream 2.1.20
does not automatically make the ChatBBC package version 2.1.20 and does not authorize a release,
tag, push, or publication.

## Core Architectural Rule

Upstream behavior is input. ChatBBC identity and ownership remain authoritative.

For every upstream change, the migration must answer these questions before implementation:

1. What meaningful fact is changing?
2. Which ChatBBC module already owns that fact?
3. What identity proves the operation belongs to the current owner?
4. What async epoch or incarnation must still match when the result returns?
5. What is presentation-only and therefore forbidden from becoming execution authority?
6. What existing downstream rule must be reapplied after the functional change?

The migration follows the current project rule: one durable fact has one authoritative owner.
Projections may read or display an owner's state; they may not independently decide it.

## Identity Boundaries That Must Survive the Port

The following identities are non-negotiable migration constraints:

- **Local work identity:** durable local session, not the replaceable ChatGPT conversation.
- **Request attribution:** normalized request id -> exact conversation -> local session epoch.
- **Browser authority:** exact conversation + Chrome document id + navigation epoch + message/turn id.
- **Input delivery:** immutable outbox UUID + local session + exact elected browser owner or exact
  tool recipient.
- **Workers:** prime family + run incarnation + exact worker conversation; `worker-1` alone is never
  globally sufficient identity.
- **Continuation:** local session + continuation token + source/destination lineage.
- **Renderer async work:** selected session/draft key + load or invocation generation.
- **Credentials:** main-process secret owner; durable encrypted write precedes publication.
- **Goal:** objective, mode, and reply debt remain separately owned by `goal.ts` ledgers.

Unknown identity continues to fail closed anywhere a wrong decision could mutate, attribute, send,
or retire state for another owner.

## Migration Strategy

Use a hybrid commit-ledger and semantic subsystem-port strategy.

Do not merge the unrelated upstream Git history into ChatBBC `main`, and do not cherry-pick the 29
commits wholesale. The fork was imported as a snapshot with fresh history and has already diverged
in core ownership, branding, packaging, bridge, theme, and release behavior.

Instead:

1. Build a complete ledger for the upstream range.
2. Group substantive behavior into independently testable port units.
3. Port each unit against the current ChatBBC owner, not against old file shape alone.
4. Record merge/release/CI-only commits as accounted-for dispositions rather than manufacturing
   duplicate source changes.
5. Advance the upstream baseline only after the complete range is accounted for.

## Upstream Commit Ledger

The implementation must maintain a durable ledger for every commit in the range. Each row records:

```text
upstream SHA
author
upstream PR when known
purpose
changed paths
classification
ChatBBC owner affected
ChatBBC adaptation rule
tests / acceptance evidence
final disposition
```

Allowed classifications are:

- `port`: behavior can be brought across substantially as-is within the same owner.
- `adapt`: behavior is useful but must be rewritten around ChatBBC ownership or product rules.
- `already-equivalent`: ChatBBC already independently implements the behavior.
- `translate`: upstream CI/release/platform intent becomes an equivalent local/Linux mechanism.
- `provenance-only`: historical/release/merge metadata is recorded but does not require runtime code.
- `intentionally-not-imported`: behavior conflicts with ChatBBC scope and the reason is recorded.

There must be no unclassified SHA between the old and new upstream anchors.

## Port Units and Order

The 29 commits collapse into a smaller set of substantive migration units. Port them in the order
below so lower-level correctness fixes land before UI and new-surface work.

### Unit 1: Worker queued-message reporting

Primary upstream commit: `e22a96779954ebc6dee9b5d541a50865611ad5ad`.

Intent: distinguish a genuinely uncertain worker message from a message that arrived after the
worker's last step and is still durably queued for the sleeping worker.

ChatBBC adaptation:

- `agents.ts` remains the single owner of worker inbox state and worker lifecycle.
- A queued row must remain scoped to the exact prime family, run incarnation, worker conversation,
  and message id.
- A sleeping reusable worker may report that late work remains queued; a terminal worker cannot.
- A new run that also contains `worker-1` must never inherit warnings, queued work, or wake behavior
  from an older run's `worker-1`.
- The fix changes reporting of existing queue truth; it must not add a parallel unread ledger.

Required regression shape: pause/finish run A, create run B with the same worker label, and prove
run A's queue cannot mutate or appear in run B.

### Unit 2: Bridge `/hello` and project-title repair

Primary upstream commit: `c7702509c6a2c1f8e96dfb04dec2a523a7e80230`.

`/hello` adaptation:

- A caller that sends no extension protocol receives unknown compatibility rather than a false
  incompatibility verdict.
- ChatBBC continues to report the ChatBBC app identity and current bridge protocol.
- Missing protocol may yield `compatible: null`; it grants no pairing, command, input, correlation,
  or session authority.
- Foreign slug and same-slug protocol mismatch remain independent fail-closed cases.

Project-title adaptation:

- `session/store.ts` remains the session/current-chat/project authority.
- Title helpers derive a projection only.
- Browser/page title evidence may help render a title but cannot overwrite project ownership or
  rebind a session.

### Unit 3: Credential invisible-character normalization

Primary upstream commit: `afbe1284fe373fddba9ac017403f7ef34251458a`.

Intent: remove invisible characters that break stored API credentials.

ChatBBC adaptation:

- Normalize at the credential owner's admission/write boundary in `secrets.ts`.
- The encrypted durable write succeeds before the in-memory cache is published.
- Consumers do not each grow their own trimming/sanitization logic.
- Linux secure-storage requirements remain unchanged; insecure fallback modes remain refused where
  ChatBBC already refuses them.
- Tests cover both accepted normalization and values that must remain byte-significant.

### Unit 4: Provider content references and unknown directives

Primary upstream commits:

- `62c897201a4ee6eee833851ce40738de3a7c77d3`
- `d011888d4ec89d819b2c1861fe30073f13dba311`
- `1348d8a28e0e36e2bbc4ca218ffc2d7622e54c95`
- `01283bbdf8b90ef09220c663bfab535dda1e3c15`

Introduce one shared content-reference/directive interpretation owner, expected at
`src/shared/content-reference.ts`, and use it from both renderer presentation and model-facing
consumers such as Goal and worker reports.

Data flow:

```text
canonical recorded assistant text
            +
same-message recorded native rendering, when available
            |
            v
shared content-reference/directive resolver
      |                         |
      v                         v
renderer presentation      model-facing text
                              |
                              v
                      Goal / worker reports
```

Rules:

- The canonical message identity remains the authority for which message is being interpreted.
- A captured native rendering answers only how that same recorded message resolved visually.
- A capture never creates conversation, session, turn, or request ownership.
- Unknown provider directives fail presentation-soft: use a valid same-message resolved capture;
  otherwise strip unsupported directive syntax and retain ordinary inner text where safe.
- Raw provider control syntax is not shown to the user when the app cannot render it.
- A capture that still contains unresolved directive text, is truncated, or belongs to a different
  message is not accepted as resolution evidence.
- ChatBBC's own supported writing-block rendering remains separate from unknown provider directives.

### Unit 5: Composer refinement

Primary upstream commit: `0e3ff776d36570e334fe012ea86e25939ddd34c7`.

Port the useful interaction and accessibility changes while preserving ChatBBC's existing composer
and delivery owners.

Desired behavior to import/adapt:

- explicit Normal / Goal / Loop mode picker;
- clearer Plan toggle;
- context-details dialog;
- improved model/thinking-effort menu;
- composer-dock motion for dynamic panels;
- improved local context display and accessibility behavior;
- upstream verification fixtures/tests where still applicable.

Ownership constraints:

- The mode picker edits draft/session intent; `goal.ts` remains authoritative for durable Goal
  objective, mode, and reply debt.
- The Plan control operates the existing generated-workflow flow. It does not replace or redefine
  MCP `update_plan`, which remains request/session progress presentation only.
- Send continues to freeze one immutable outbox payload. UI state cannot bypass outbox admission or
  browser/tool delivery ownership.
- New Chat and existing-session drafts remain keyed by the current ChatBBC draft/session identity.
- Navigation and late async planner/model results must still prove their originating draft/session
  invocation before publication.
- Model choices remain observations of provider availability; renderer selection cannot manufacture
  availability or act as a send receipt.
- Context values remain clearly labeled local estimates and never become claims about provider
  billing or private ChatGPT context state.
- Composer animation may animate presentation but may not persist measured height as durable state.
- Incoming CSS must use ChatBBC's existing appearance/Omarchy projection rather than introducing a
  second theme system or hard-coded upstream palette owner.

Browser-facing composer/model changes require real signed-in ChatGPT acceptance in addition to
renderer tests.

### Unit 6: Opt-in local control API

Primary upstream commit: `3b792d9071dd507fcb0c43a94de37c3227504ba7`.

Port this as a separate, read-only loopback projection of existing owners. It is not a fourth MCP
surface and not another bridge.

Intended data flow:

```text
existing authoritative owners
  connection / bridge / plugins / updater / call context
                         |
                         v
              allowlisted projection
                         |
                         v
               127.0.0.1 control API
```

The control API owns zero application facts.

Required security and lifecycle rules:

- disabled by default, including malformed/legacy config recovery;
- binds loopback only on an ephemeral port;
- per-process random bearer token stored privately under userData;
- token is never issued over HTTP;
- reject requests carrying a browser `Origin`;
- GET only, no request bodies;
- authenticate before charging the per-minute request budget;
- response schema is an explicit allowlist, never owner-object serialization;
- never expose MCP tokenized paths, tunnel identifiers, browser/bridge credentials, plugin source
  configuration, API keys, or other secrets;
- clean disable/quit removes discovery/token files;
- shutdown is terminal for the process: a late settings save cannot reopen the listener;
- startup/shutdown lifecycle is serialized so stale async completions cannot publish a dead listener.

The API may project connection, bridge, plugin, updater, and in-flight call status, but it must not
mutate any of them.

### Unit 7: CI, release, version, and provenance commits

This unit accounts for release-prep, merge, hosted-workflow, version, changelog, and standalone
extension packaging commits that do not map 1:1 to ChatBBC runtime behavior.

Rules:

- `.github/workflows/*` remain absent.
- macOS Intel runner retry behavior is provenance-only unless it contains a platform-independent
  verification rule worth translating into local scripts.
- useful verification intent is translated to local Linux/Wayland scripts.
- standalone companion packaging/stamping checks are adopted only if they apply to ChatBBC's local
  companion artifact path.
- upstream package/manifest/version bumps do not overwrite ChatBBC package identity or version.
- upstream release notes may be retained as provenance or summarized in the migration ledger, but
  they do not become ChatBBC release notes.
- no tag, release, push, or publication happens as part of the source migration.

## Upstream Map Expansion

The old baseline-to-new-baseline diff changes 61 paths. At design time, 26 of those paths are not
represented in the current downstream map because they either did not differ from the old baseline
or did not exist yet.

Examples include:

- `src/shared/content-reference.ts`
- `src/main/control-api.ts`
- `src/shared/control-api.ts`
- `src/main/config.ts`
- `src/preload/index.ts`
- `src/renderer/chat.ts`
- `src/renderer/chat-models.ts`
- `src/renderer/composer-motion.ts`
- `src/renderer/context-meter.ts`
- composer verification scripts and fixtures
- new or newly relevant tests

The implementation must not blindly add all 26 paths to the map. After each semantic port, compare
ChatBBC against the new upstream baseline and map exactly the paths that intentionally remain
different.

Expected new or expanded map categories include:

- `content-reference`
- `control-api`
- `composer`
- `verification`
- `identity`
- `linux-release`
- `local-automation`
- `documentation` / provenance

Each mapped path requires a specific `decision`, `portRule`, and checks. A catch-all rule such as
"keep downstream changes" is not acceptable.

## Baseline Advancement Rule

During partial implementation, keep the map's full-import upstream baseline at
`dee4b5e94b8598d7630e6db62bada9ac6050f457` and record adopted work through exact port records.

Advance the baseline only when:

1. all 29 commits have a final ledger disposition;
2. every changed path is accounted for against the new baseline;
3. all required source/test/build/UI/browser gates pass;
4. provenance and retained-identifier exceptions are updated precisely.

Only then update the map to:

```json
{
  "commit": "4e51a04d8e89a559e16d17fc7df6f547e57d666d",
  "version": "2.1.20"
}
```

This makes `4e51a04…` the next clean synchronization point.

## Testing and Verification

### Unit-level testing

Each port unit starts with a failing regression test at the current ChatBBC owner. Tests should
exercise ownership/race behavior, not only happy-path output.

Important cases include:

- worker run A and run B both use `worker-1`; no queue/report state crosses run incarnation;
- protocol-less `/hello` is unknown rather than incompatible but gains no authority;
- a page title cannot replace durable project/session ownership;
- credential normalization occurs before durable secret publication;
- a content-reference capture from another message/turn cannot resolve the current message;
- an unresolved/truncated provider-directive capture cannot become model-facing content;
- planner/model result for draft A returns after navigation to draft B and cannot overwrite B;
- A -> B -> A navigation does not let an old composer invocation publish into the new generation;
- old model observation arriving after a newer selection/session state cannot republish stale UI;
- control API start -> disable -> late async completion cannot republish the listener;
- control API shutdown -> later config/settings activity cannot reopen it;
- control API status projection contains no secret-bearing connector/bridge fields.

### Project gates

At minimum, after relevant targeted tests:

```bash
npm run verify:upstream-map
npm run verify:rebrand
npm run typecheck
npm run verify
npm run build
npm run verify:ui
```

Run the project's local Linux x64 packaging/smoke gates when source integration is complete.

### Live evidence

Use evidence labels accurately:

- unit/source tests prove source behavior only;
- build proves compilation/bundling only;
- local package smoke proves packaged-runtime behavior only;
- renderer fixtures do not prove native ChatGPT behavior;
- browser-facing content-reference, companion, and composer/model changes require a real signed-in
  ChatGPT page for final live acceptance.

Do not claim a provider-cached connector, native model menu behavior, or companion flow is verified
unless it was actually exercised with an authorized live account.

## Documentation and Provenance

Preserve upstream MIT attribution and author/PR credit for incorporated work.

The migration should update:

- `docs/UPSTREAM.md` with the new baseline and any new port procedure details discovered during the
  migration;
- `docs/upstream-map.json` with exact downstream ownership and retained identifiers;
- current ChatBBC setup/security docs for adopted control-API behavior using ChatBBC naming;
- current product documentation only where behavior actually changed.

Historical upstream release notes and worklogs remain historical evidence; they do not become
current ChatBBC instructions by being copied.

## Review and Commit Boundaries

Implementation should land in independently reviewable commits approximately along these semantic
boundaries:

```text
port: repair worker queued-message reporting
port: repair bridge hello and project titles
port: normalize stored API credentials
port: resolve ChatGPT content directives
port: adapt upstream composer refinements
port: add read-only local control API
docs: account for upstream 2.1.18 to 2.1.20
chore: advance upstream baseline to 4e51a04
```

Exact boundaries may combine a tiny provenance-only step with its owning functional unit, but they
must not collapse the migration into one opaque "sync upstream" commit.

Every functional commit must include its targeted tests. The final baseline-advance commit is only
allowed after all earlier migration commits are independently green.

## Non-Goals

This migration does not:

- merge upstream Git history into ChatBBC;
- restore hosted GitHub Actions;
- add Windows, macOS, or ARM release support;
- rename ChatBBC back to upstream identifiers;
- replace ChatBBC's bridge protocol, session/outbox ownership, worker run identity, Goal ledgers, or
  Omarchy appearance owner with upstream alternatives;
- create a fourth MCP surface from the local control API;
- turn provider page rendering into execution or conversation identity evidence;
- publish a new ChatBBC release.

## Final Acceptance

The migration is accepted when the repository can explain, for every upstream commit and every
changed path in the 2.1.18 -> 2.1.20 range, exactly what ChatBBC did with it and why; all retained
behavior runs through the current ChatBBC owner; identity/race regressions are covered; the map
points at the new baseline without exceptions that merely hide divergence; and live browser-facing
flows have been exercised at the evidence level they require.
